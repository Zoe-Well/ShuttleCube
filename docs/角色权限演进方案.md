# ShuttleCube 角色权限演进方案

## 1. 当前产品决定

ShuttleCube 当前版本只面向场馆管理人员，不向用户开放多角色或自定义权限配置。所有正常启用的业务账号统一显示为“场馆管理人员”，拥有相同的场馆管理能力。

当前版本不提供：

- 运营人员、财务人员、教练等角色选择；
- 按账号隐藏不同业务页面；
- 自定义勾选权限；
- 只允许查看本人数据的员工账号；
- 面向员工的独立前端。

这样可以保证第一版产品简单、可理解，也避免在真实人员分工尚不明确时过早固化权限模型。

## 2. 当前版本仍需保留的安全基础

不开放多角色，不等于删除安全基础。当前仍应保留：

1. 登录、会话和 CSRF 防护；
2. Organization／Venue 数据归属与作用域校验；
3. 服务端 capability 检查框架；
4. 高风险操作的人工确认或审批；
5. 收款、退款、考勤、补排、设置修改等操作审计；
6. 智能运营模型、Tool 和业务接口的字段投影与权限边界；
7. 跨场馆、跨机构和直接引用其他记录时的服务端拒绝。

这些能力当前可以统一由“场馆管理人员”权限包满足，不需要暴露给最终用户。保留它们可以避免未来增加运营人员账号时重新改造所有接口。

## 3. 当前项目建议调整

### 3.1 用户界面

- 创建或初始化账号时不要求选择角色，统一显示为“场馆管理人员”；
- 运营设置中暂不展示成员角色和 capability 明细；
- 设置页文案不再强调“成员权限”，只保留当前实际需要的运行、AI 和运营规则设置；
- 不按角色拆分侧边栏、路由或页面；
- 不创建多套前端项目。

### 3.2 案件中的“负责人”

案件负责人不是系统权限角色，而是该案件的实际跟进人。

为避免误解，界面建议统一使用“处理人”“当前处理人”“由我处理”和“分配处理人”。如果当前部署只有一个账号，可以隐藏分配区域；如果有多个权限相同的场馆管理账号，可以继续用处理人进行内部协作，但不会因此改变任何人的页面或数据权限。

### 3.3 后端与数据结构

- 当前正常账号统一解析为完整的场馆管理 capability 包；
- 暂不开放角色修改 API 和角色管理 UI；
- 保留 OrganizationMembership、VenueMembership、role_key 和 capability registry；
- 不删除现有 scope、字段投影、审批和审计代码；
- 不为了单角色版本给所有旧业务接口补一套没有实际差异的角色判断；
- 新增接口仍使用服务端 scope 和必要的 capability 检查，避免未来返工。

### 3.4 文档与测试

- 当前验收只验证已登录的场馆管理人员能够使用全部功能；
- 继续验证未登录、跨场馆、跨机构、越权引用和高风险审批边界；
- 暂不把多角色菜单差异、财务字段隔离和员工账号权限矩阵作为当前版本验收条件；
- 多角色相关测试可以保留为未来安全基础，但不应阻塞当前单角色产品体验。

## 4. 后续双角色方案

当场馆开始给普通员工分配独立账号，或明确要求员工不能查看工资、利润和完整财务时，再启用多角色功能。第一阶段只提供两个固定角色，不开放自定义权限。

### 4.1 场馆负责人

- 查看和操作所有页面；
- 查看完整收款、支出、利润和工资；
- 执行退款、作废和其他敏感财务操作；
- 管理账号、场馆设置、运营规则和 AI 设置；
- 审批高风险操作并查看操作审计。

### 4.2 运营人员

- 查看和处理排期、课程、考勤、学员、场地及运营案件；
- 为完成具体业务查看对应的单笔应收、已收、退款和待收；
- 登记当前业务或当前案件对应的实际收款；
- 不进入完整财务、支出、利润、工资和结算页面；
- 不执行退款、作废流水、账号管理、系统设置和高风险审批。

运营人员的财务边界统一表述为：

> 可以为了完成具体业务查看和登记这一笔钱，但不能查看整个场馆的钱。

## 5. 后续技术实现方式

未来仍使用一套前端和一套后端。

前端根据服务端返回的 capabilities 过滤菜单、保护路由、控制敏感按钮和字段。后端负责最终权限裁决：

- 每个接口声明读取或写入 capability；
- 所有查询校验 Organization／Venue scope；
- 单笔财务读取必须绑定当前业务或已授权案件；
- 完整财务、利润和工资接口只允许场馆负责人；
- 退款、作废、审批和设置修改分别校验操作权限；
- 前端隐藏不能代替服务端 403；
- 建立 owner／operator 权限矩阵和越权自动化测试。

用户创建账号时只需要选择“场馆负责人”或“运营人员”。细粒度 capability 仅作为内部技术实现，不暴露为复杂的权限勾选界面。

## 6. 未来迁移顺序

1. 确认 owner／operator 页面、操作和字段矩阵；
2. 给现有账号统一迁移为 owner，避免升级后丢失权限；
3. 对完整财务、工资、利润、退款、作废、审批和设置接口增加服务端强制校验；
4. 为单笔业务收款建立明确的业务对象或案件授权边界；
5. 增加前端菜单过滤、路由保护和按钮控制；
6. 增加账号管理页面，只提供两个角色模板；
7. 完成直接 URL、直接 API、跨业务记录和字段泄露测试后再开放运营人员账号。

## 7. 当前不应进行的工作

- 不复制两套前端；
- 不为每个员工创建独立页面版本；
- 不开放几十项 capability 自定义勾选；
- 不删除已经存在的 scope、capability、审批和审计基础；
- 不仅通过隐藏菜单实现安全隔离；
- 不在尚无普通员工账号需求时改造全部现有业务流程。

## 8. 最终结论

当前版本保持单一“场馆管理人员”角色，优先完成业务闭环和智能运营体验。代码层保留未来扩展所需的 scope、membership、capability、字段投影、审批和审计基础，但不向当前用户展示复杂角色配置。

后续出现员工独立账号需求时，再启用“场馆负责人／运营人员”两角色方案，并通过同一套前端的权限自适应和后端强制授权实现，不建设多套前端。
